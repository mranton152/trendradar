# Как мы работаем втроём

Трое вайбкодят параллельно тремя разными моделями. Без жёсткого процесса это
за два дня превращается в кашу из конфликтов. Правила ниже — не бюрократия,
а единственный способ не потерять неделю на слияниях.

## Состав

| Кто | Роль | Папки | Модель | Железо |
|---|---|---|---|---|
| **Антон** | капитан, ядро методологии, интеграция | `core/`, `validation/`, `contracts/`, `docs/` | Claude Opus 5 | MacBook Pro M4 Pro, 24 ГБ |
| **Константин** | данные и семантика | `ingest/`, `semantic/` | ChatGPT 5.6 | RTX 3070 Laptop, i7-12700H, 32 ГБ |

## Золотое правило

**Ты пишешь только в свои папки.** Всегда. Даже если «там очевидная опечатка»,
даже если «модель сама предложила поправить». Нашёл проблему у соседа — пиши
в чат или заводи issue.

Причина простая: три LLM, которые правят один файл, гарантированно устроят
конфликт слияния, и разбирать его будет человек, который этот код не писал.

## Ветки

```
main                       ← всегда рабочий, всегда зелёный CI
  feat/anton/scoring-v2
  feat/kostya/openalex-connector
  feat/misha/trend-card
```

- Ветка живёт **максимум сутки**. Не копи неделю работы в ветке.
- Имя: `feat/<имя>/<короткая-задача>` либо `fix/`, `docs/`.
- В `main` пушим только через Pull Request.

## Цикл дня

1. Утром: `git checkout main && git pull` — обязательно, до начала работы.
2. `git checkout -b feat/<имя>/<задача>`
3. Работаешь. Коммитишь часто, мелко, по-русски осмысленно.
4. `make check` — линт, тесты, валидация контрактов. Красное — не пушим.
5. `git push -u origin feat/<имя>/<задача>` → открываешь PR.
6. Антон ревьюит и мержит. При тривиальном PR в свою папку — мержим сами
   после зелёного CI, но обязательно с открытым PR (нужна история для жюри).
7. Вечером в 21:00 — синк в телеграме: что сделано, что блокирует, что завтра.

## Что делать при конфликте слияния

Конфликт в **своей** папке — решаешь сам.
Конфликт в **общей** (contracts, docs, pyproject, Makefile) — не решай сам,
пиши Антону. Это почти всегда означает, что два человека полезли в одно место.

**Частный случай: `__init__.py`.** При разметке каркаса Антон создал пустые
`__init__.py` во всех рабочих папках, включая чужие. Если твой ассистент создаст
свой такой же файл, при ребейзе получится конфликт add/add. Решение: **оставляй
свою версию**, она в твоей папке и она главная.

```bash
git checkout --theirs ingest/__init__.py    # при rebase «свои» это theirs
git add ingest/__init__.py
```

## Важно: конфликт блокирует CI целиком

Пока PR конфликтует с `main`, GitHub **не запускает проверки вообще** — ему не из
чего собрать пробное слияние. Поэтому «проверок нет» почти всегда означает не
поломку CI, а неразрешённый конфликт. Лечится ребейзом:

```bash
git fetch origin && git rebase origin/main
# разрешить конфликты, затем
git push --force-with-lease
```

## Контракты

`contracts/schemas.py` — закон. Менять может только Антон.
Нужно новое поле → issue с меткой `contract` → обсудили → Антон вносит одним PR →
все делают `git pull`.

Пока контракт соблюдается, ты можешь переписывать свою половину как угодно,
хоть с нуля, и никого этим не сломаешь. В этом весь смысл.

## Данные

- В git едет только **золотой снапшот** `data/index/golden/` (~50 МБ) — маленький
  настоящий срез одного домена. Все тесты и вся разработка идут на нём.
- Полные корпуса (десятки ГБ) — в **GitHub Releases**, качаются `make pull-corpus`.
- Кэш ответов API (`data/cache/`) — локальный, в git не едет никогда.

## Коммиты

По-русски, повелительное наклонение не обязательно, главное — понятно, что и зачем.

```
Коннектор arXiv: постраничная выборка с кэшем

arXiv отдаёт максимум 2000 записей за запрос, поэтому идём окнами по годам.
Ответы кэшируются на диск, повторный прогон бесплатный.
```

Один коммит «initial commit» в конце хакатона выглядит для жюри плохо.
Честная история коммитов — часть сдачи.

## Что делает CI на каждый PR

1. `ruff check` — линт Python.
2. `pytest` — тесты, включая тесты на метрики скоринга.
3. `python contracts/validate.py` на золотом снапшоте — все parquet соответствуют схемам.
4. Проверка границ: PR не должен трогать чужие папки (`.github/workflows/ownership.yml`).

## Что НЕ делаем

- Не пушим в `main` напрямую.
- Не меняем стек по ходу («а давайте на Go»).
- Не рефакторим чужое.
- Не оставляем закомментированный код и «на всякий случай» файлы.
- Не кладём секреты в репозиторий — только `.env`, он в `.gitignore`.
